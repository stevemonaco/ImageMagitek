# Startup survives bad resource files and any working directory

## Why

TileShop.UI stops at startup on any one bad file in its resource folders, and finds no resources at all when launched from a shortcut or shell whose working directory is not the install directory. None of these items were tagged 1.0; all are promoted here because an installed 1.0 that will not start fails the "dependable" goal (ARCHITECTURE §1) more completely than any single broken feature: the user loses access to every project, with no message saying why.

Backlog items covered, each confirmed in the code:

- [LIB-SERVICES] The UI resolves `appsettings.json`, `_palettes`, `_codecs`, `_plugins`, `_layouts` and both schemas against the working directory (`TileShopBootstrapper.ConfigureImageMagitek` passes the relative `BootstrapService.Default*` names); the CLI combines them with `AppContext.BaseDirectory`. From another directory the UI gets default settings (the file is "missing"), then `ReadJsonPalette` throws `FileNotFoundException` and the app exits. `PreferencesViewModel` also lists NES palettes from the relative `_palettes`, and the UI log `errorlog.txt` lands in the working directory. Promoted: launching from a shortcut is the normal way to start an installed app.
- [ARCHITECTURE] Startup tolerance is inconsistent: invalid XML codecs and unreadable layouts are logged and skipped; malformed codec XML, plugin load errors, missing or malformed palettes stop startup. Promoted: the rule this change records is what makes every other item consistent.
- [LIB-CODECS] `XDocument.Load` in `XmlGraphicsFormatReader.LoadFromFile` throws `XmlException` on a file that is not well-formed, out through `XmlCodecService.LoadCodecs` and `CreateCodecService`. `PluginService.LoadCodecPlugins` lets `LoadDefaultAssembly()`/`GetTypes()` failures (`ReflectionTypeLoadException`, `BadImageFormatException`, `FileLoadException`) escape, and `CodecFactory.AddOrUpdateCodec` instantiates the type, so a throwing constructor escapes as `TargetInvocationException` (a type with no supported constructor as `ArgumentException`). Also found: a missing `_codecs` folder throws `DirectoryNotFoundException`, and a missing `CodecSchema.xsd` throws `ArgumentException` from the reader's constructor. Promoted: one user-added codec or plugin file must not make the app unusable.
- [LIB-PALETTES] `CreatePaletteStore` catches only `InvalidDataException`; `FileNotFoundException` and `JsonException` escape, and with no global palette `globalPalettes.First()` throws. Promoted: same reason.
- [LIB-PALETTES] The NES master palette's ≥ 64-entry check is in the UI bootstrapper only, and only for the user-preference override; a short palette named by `appsettings.json` passes in both hosts and makes Nes indices past its end throw on conversion. Promoted: a short master palette breaks every NES project, far from its cause.
- [LIB-ARRANGERS] `ElementLayoutService.ReadLayout` lets `JsonException` escape (also `ArgumentNullException` from the `TileLayout` constructor when `pattern` is missing), and `CreateElementStore` uses `Dictionary.Add`, so a duplicate name throws. Promoted: same reason as codecs.
- [LIB-CODECS] `CodecFactory` keeps C# codecs and XML formats in separate dictionaries; `CreateCodec` prefers the C# one, so a plugin named like an XML codec silently shadows it, and `GetRegisteredCodecNames` concatenates both key sets, listing the name twice. No shipped codec collides today. Promoted: which codec a project's elements decode with must not depend on which plugins happen to be installed.
- [LIB-SERVICES] `AppSettings` is a positional record deserialized with System.Text.Json, so an omitted key becomes null and throws later where it is used (for example `settings.GlobalPalettes` in `CreatePaletteStore`). A malformed file is logged as critical and rethrown (LIB-SERVICES-004). Promoted: a hand-edited `appsettings.json` is a user-added file like any other.

How failures surface today: the UI has no handler. An exception in `App.OnFrameworkInitializationCompleted` reaches `Program.Main`, which logs it as fatal and rethrows, so the process ends with no window and no message. The UI logger's minimum level is Error, so the warnings for skipped layouts are never written. The CLI wraps bootstrap in a try/catch, logs the exception as fatal (console and `errorlogCLI*.txt`) and exits -4; it prints warnings and errors to the console.

## What

Shipped resources resolve against the application directory in both hosts, whatever the working directory.

Startup loads each resource file on its own. A bad file (malformed, unreadable, invalid, or a name already taken) is logged, skipped and recorded as a startup issue; everything else loads. Startup fails only when something essential cannot be loaded: `CodecSchema.xsd`, `ResourceSchema.xsd`, at least one global palette, and an NES master palette with at least 64 entries.

The UI shows the recorded issues in one alert after the main window opens, and, when startup fails, a small error window naming the cause and the log file instead of exiting silently. The UI log moves to `%LOCALAPPDATA%/TileShop/` and includes warnings. The CLI prints each issue as a warning and carries on; a fatal issue still exits -4.

Codec names are unique across built-in, XML and plugin codecs: the first registration wins and a later collision is a startup issue. A partial `appsettings.json` takes the built-in default for each omitted key; a malformed one falls back to the defaults and is reported.

Unchanged: the default resource names, the XML codec duplicate rule (first file wins), legacy codec name resolution, the CLI's exit codes, the CLI not loading plugins (CLI-COMMANDS-008, a separate 1.0 item), the CLI's log location and `--log` (separate 1.0 item), and unhandled exceptions after startup (still logged and fatal).

## Decisions

- **Shipped resources resolve against the application directory.** A `BootstrapPaths` record (settings file, palettes, codecs, plugins, layouts, both schemas) built by `BootstrapPaths.FromDirectory(string)`; both hosts use `FromDirectory(AppContext.BaseDirectory)`, and the UI registers it in DI for `PreferencesViewModel`. `AppContext.BaseDirectory` is the executable's directory for single-file publishes too. Reason: one place for the rule, testable with a temp directory, and it removes the CLI's six `Path.Combine` lines. Rejected: `Directory.SetCurrentDirectory` at startup (a process-wide side effect that would break relative paths users pass to the CLI and file dialogs that start in the working directory); fixing only the UI's call sites (the next caller repeats the bug).
- **Startup degrades instead of stopping (project-wide, ARCHITECTURE §6).** Each file in `_codecs`, `_plugins`, `_palettes`, `_layouts`, and the settings file, loads independently; a failure is logged, skipped and reported once to the user. Reason: a user-added file is the likeliest thing to be broken, and the rest of the app does not depend on it. Rejected: failing fast on any bad file (current behavior for half the folders: one bad download makes the app unusable); skipping silently (a project that needs the skipped codec then fails with an error that does not name the cause).
- **Essentials are the two schemas, a global palette and a 64-entry NES master palette.** Without a schema no XML codec or project loads; the default palette is passed to the codec factory and every indexed codec; without a valid master palette every Nes-model palette fails at project load with an `ArgumentException` that names nothing (LIB-COLORS-022). All four ship with the app, so their absence means a broken install that a reinstall fixes. A missing `_codecs` or `_layouts` folder is an issue, not fatal (the app still opens projects using built-in codecs); a missing `_plugins` folder is normal and not reported. Rejected: embedding fallback copies of `DefaultRgba32`/`DefaultNes` as assembly resources (duplicates shipped data and masks a broken install); treating the NES master palette as optional (moves the failure to a confusing place).
- **The NES master palette override falls back inside the library.** `CreatePaletteStore` takes an optional override name; if that palette is missing, malformed or under 64 entries it records an issue and loads the settings' NES palette, which is fatal only if it is also unusable. Reason: the UI's two-pass fallback (UI-SHELL-056) existed only because the library did no validation; moving it puts the 64-entry rule in one place and the CLI gets it too. Rejected: keeping the check in the UI (the CLI stays unchecked).
- **Issues are collected on the bootstrap service; essentials throw one exception type.** `BootstrapService.Issues` is a list of `StartupIssue(string Path, string Message, bool IsFatal)`, appended by every factory member as it logs. An essential failure records a fatal issue and throws `BootstrapException`, which each host catches once around its bootstrap sequence. Reason: every later step needs the previous one's result (the codec factory needs the default palette), so there is nothing to continue with; one catch per host is simpler than threading a `MagitekResult` through every factory member and its overrides. Rejected: `MagitekResult` returns from each factory member (changes every overridable signature for a failure the host can only report); parsing the log (fragile).
- **The UI reports issues in one alert per launch.** After the main window opens, if there are non-fatal issues, an alert headed "Some resources were not loaded" lists each file name and its first reason line (at most 20, then "and N more"), followed by the log file path. It reappears every launch until the file is fixed or removed. Reason: an alert is seen; the user can act on it (remove the file); the log keeps the full reasons. Rejected: status-bar text (cleared after 2 s, easily missed); log only (users do not read logs, and today the UI does not even log warnings); listing issues in About only (nobody looks there until something is already broken).
- **A fatal startup error shows its own window.** When bootstrap throws, `App` sets the main window to a minimal `StartupErrorWindow` (message, log path, a Close button) instead of the shell; closing it exits. Any exception during bootstrap, not only `BootstrapException`, takes this path. Reason: the overlay dialog host needs the shell, which cannot be built without the bootstrapped services. The window is created directly, not through DI or `ViewLocator`, because neither exists yet. Rejected: a third-party message-box package (new dependency for one window); exiting with only a log line (current behavior).
- **The UI log moves to `%LOCALAPPDATA%/TileShop/` and logs Warning and above.** Next to `preferences.json`. Reason: the application directory may be read-only under Program Files, and the working directory scatters log files wherever the app was launched; skipped files are warnings, so an Error minimum would hide exactly what the alert points to. Rejected: the application directory; keeping Error.
- **The CLI's exit code ignores non-fatal issues.** Issues print as warnings and go to the log; the exit code is unchanged, and fatal issues exit -4 as today. Reason: a toolchain should not break because of an unrelated bad codec file; if the project needs a skipped codec, opening it fails with -5. Rejected: a new "degraded" exit code (breaks toolchains that only check for zero).
- **Codec names are unique; the first registration wins.** Registration order is built-in C# codecs, then XML codecs in ordinal file order, then plugins in directory order. A later registration under a taken name (any source) is refused and reported naming both sources. `AddOrUpdateCodec`/`AddOrUpdateFormat` become `AddCodec`/`AddFormat` returning a `MagitekResult`. Reason: a project names codecs, so which bytes-to-pixels mapping it gets must not depend on installed plugins; shipped codecs are the trusted ones. Generalizes LIB-CODECS "Duplicate XML names keep the first file". Rejected: C# codecs win (current, silent); last registration wins; renaming the newcomer (projects could not refer to it predictably). Legacy names are unaffected: they are not registered names, so a plugin may still claim one (LIB-CODECS "Legacy names resolve last").
- **A plugin DLL that fails to load is skipped whole.** Any exception while loading the assembly or enumerating its types skips that plugin directory. Reason: types from a partially loaded assembly can fail later when a member touches a missing dependency. Rejected: registering the loadable types from `ReflectionTypeLoadException.Types`. A type whose construction throws, or that has no supported constructor, is skipped on its own.
- **Settings merge per member, not per key.** After deserializing, each null member (and an empty global palette list) takes the built-in default. A present `extensionCodecAssociations` replaces the default dictionary entirely. Reason: a user who writes the dictionary means it; key-level merging would make an association impossible to remove. A malformed settings file is not essential: bootstrap records an issue and uses the defaults. Rejected: key-level merge; failing startup on malformed settings (the code has defaults, so nothing essential is missing).
- **Layout files load in ordinal order, first name wins, and a layout must be usable.** `ReadLayout` fails, instead of throwing, on malformed JSON, a missing or empty pattern, a width or height below 1, a pattern cell outside the width × height, or a `tilesPerPattern` different from the pattern's length. Reason: the same rule as codecs; an out-of-range pattern would throw later in the graphics editor. Rejected: last wins (directory order is unspecified).

## Spec changes

**docs/ARCHITECTURE.md §6:** add

- **Startup degrades; it stops only for essentials.** Each file in `_codecs`, `_plugins`, `_palettes` and `_layouts`, and the settings file, loads on its own: a bad one is logged, skipped and reported to the user once per launch (the UI's startup alert, the CLI's console), and the rest load. Startup fails, naming the file, only when an essential is missing or unusable: `CodecSchema.xsd`, `ResourceSchema.xsd`, a global palette, or an NES master palette of at least 64 colors. Shipped resources resolve against the application directory, never the working directory. See LIB-SERVICES.

**LIB-SERVICES** (add `BootstrapPaths`, `StartupIssue`, `BootstrapException` to `types`; add `BootstrapServiceTests` to `tests`):

- Changed **LIB-SERVICES-004** — If the settings file exists but cannot be read as settings JSON, then bootstrap shall log it, record a startup issue naming the file and return the built-in defaults.
- Changed **LIB-SERVICES-008** — When a settings file omits a key, or gives an empty global palette list, bootstrap shall use the built-in default for that setting; a key that is present replaces the default as a whole.
- Changed **LIB-SERVICES-013** — The default locations shall be `appsettings.json`, `_palettes`, `_codecs`, `_plugins`, `_layouts`, `_schemas/ResourceSchema.xsd` and `_schemas/CodecSchema.xsd`, resolved against a given directory; hosts shall pass the application directory, so the working directory never affects which resources load. (Drops `(inherited)`: now a decision. The log file default moves to the hosts' specs.)
- Added — Each bootstrap factory member shall record a startup issue (file path, reason, whether fatal) for every file it logs and skips, and the host shall be able to read the issues after bootstrapping.
- Added — If an essential resource (the codec schema, the resource schema, every global palette, or a usable NES master palette) cannot be loaded, then bootstrap shall record a fatal issue naming it and throw `BootstrapException`.
- Edge cases: delete "A partial settings file yields null members that later throw…".
- Open items: delete the LIB-SERVICES-008 and LIB-SERVICES-013 lines.
- Decisions: add "Shipped resources resolve against the application directory", "Issues are collected on the bootstrap service; essentials throw one exception type", "Settings merge per member, not per key".

**LIB-PALETTES:**

- Changed **LIB-PALETTES-034** — When the bootstrapper creates the palette store, it shall load `<palettes>/<name>.json` for each name in the settings' global palettes, in order, and log, record as a startup issue and skip any that is missing, malformed or empty.
- Changed **LIB-PALETTES-036** — When the bootstrapper creates the palette store with an NES palette override, it shall use the override if it loads with at least 64 entries; otherwise it shall record a startup issue and load the settings' NES palette.
- Added — If no global palette loads, then creating the palette store shall fail as an essential resource (LIB-SERVICES).
- Added — If the settings' NES master palette is missing, malformed or has fewer than 64 entries, then creating the palette store shall fail as an essential resource (LIB-SERVICES).
- Edge cases: delete "An NES master palette with fewer than 64 entries … only the UI checks the count."
- Open items: delete the `CreatePaletteStore` catches only `InvalidDataException` line; drop "or the palette store" from the missing-tests line.
- Decisions: reword "The NES master palette is configurable" to say the override is passed to `CreatePaletteStore`, which validates it and falls back; add "Essentials are the two schemas, a global palette and a 64-entry NES master palette" (or refer to LIB-SERVICES if it lives there).

**LIB-CODECS:**

- Changed **LIB-CODECS-033** — When a file fails to load, including a file that is not well-formed XML, the service shall report its name and reasons and continue with the remaining files; the overall result fails if any file failed.
- Changed **LIB-CODECS-034** — When the bootstrapper creates the codec service, it shall log and record as a startup issue every load failure and continue with the codecs that loaded; a missing codec folder is an issue, and a missing codec schema is fatal (LIB-SERVICES).
- Struck **LIB-CODECS-036** — Removed: names are unique across C# codecs and XML formats, so there is nothing to prefer.
- Changed **LIB-CODECS-043** — When a codec type is added, the factory shall instantiate it to read its name and register it under that name; if the name is already registered as a C# codec or an XML format, or instantiation throws, then it shall return a failure naming the type and leave the registry unchanged.
- Changed **LIB-CODECS-045** — The factory's registered names shall list each XML format and C# codec once, in sorted order, excluding legacy names.
- Changed **LIB-CODECS-056** — When plugins are loaded from a directory, the plugin service shall load `<sub>/<sub>.dll` from each immediate subdirectory that has one, in its own load context sharing `IGraphicsCodec`, and collect every non-abstract type implementing `IGraphicsCodec`; if loading the assembly or enumerating its types throws, then it shall report that plugin and skip it.
- Changed **LIB-CODECS-057** — When the bootstrapper creates the plugin service, it shall load plugins only if the plugin directory exists, register each discovered type with the codec factory, and log and record as a startup issue each plugin or type that fails to load or register.
- Added — If an XML format is added under a name already registered as a C# codec or XML format, then the factory shall return a failure and keep the existing registration.
- Edge cases: delete the `XmlException`, plugin-load and shadowing lines.
- Open items: delete "Malformed XML codec files, plugin load failures and throwing plugin constructors are not caught…" and "A C# codec registered under an XML codec's name shadows it silently…"; drop "the bootstrapper's codec and plugin paths" from the missing-tests line.
- Decisions: replace "Duplicate XML names keep the first file" with "Codec names are unique; the first registration wins" (keeping its history); add "A plugin DLL that fails to load is skipped whole".

**LIB-ARRANGERS:**

- Changed **LIB-ARRANGERS-042** — When a layout file is read, the layout service shall return the layout, or fail naming the file when it does not exist, is not valid JSON, deserializes to nothing, or describes an unusable layout (width or height below 1, a missing or empty pattern, a cell outside the layout, or a tile count different from the pattern's length); property names match case-insensitively.
- Changed **LIB-ARRANGERS-043** — At bootstrap, the element store shall read the layouts folder's files in ordinal name order and hold each layout that reads by name; it shall log and record as a startup issue each file that fails to read and each later file whose name is already held, and be empty when the folder is missing.
- Decisions: add "Layout files load in ordinal order, first name wins, and a layout must be usable".

**UI-SHELL:**

- Changed **UI-SHELL-056** — At startup, the app shall pass the NES override to the palette store, which falls back to the appsettings.json NES palette when the override is unusable (LIB-PALETTES), and the fallback shall appear in the startup alert.
- Changed **UI-SHELL-104** — The app shall log Warning and higher messages to a monthly rolling log file in `%LOCALAPPDATA%/TileShop/`. (Drops `(inherited)` once confirmed; see Open questions.)
- Added — When startup records non-fatal issues, the shell shall show, once after the main window opens, an alert headed "Some resources were not loaded" listing each file and reason (at most 20, then a count of the rest) and the log file path.
- Added — If bootstrapping throws, then the app shall show a startup error window with the message and the log file path instead of the main window, and exit when it is closed.
- Added — The NES palette list in the Preferences dialog shall come from the application directory's `_palettes`.
- Edge cases: delete "An NES override that is ignored at startup … is not reported to the user"; keep the clause that the Preferences dialog still shows the ignored override selected.
- Open items: reword "Unhandled exceptions are not caught or shown…" to cover only exceptions after startup.
- Decisions: add "The UI reports issues in one alert per launch", "A fatal startup error shows its own window", "The UI log moves to `%LOCALAPPDATA%/TileShop/`".

**CLI-COMMANDS:**

- Changed **CLI-COMMANDS-007** — If an essential resource cannot be loaded from the application directory (LIB-SERVICES), then the CLI shall log the failure and exit with -4; other startup issues shall be printed as warnings and shall not change the exit code.
- Decisions: add "The CLI's exit code ignores non-fatal issues".

## Open questions

- UI-SHELL-104 is inherited ("log errors only"). This change raises it to Warning and moves the file from the working directory to `%LOCALAPPDATA%/TileShop/`. Recommendation: confirm both, so the log the startup alert points to contains the skipped files and is in one known place.
- Should the startup alert repeat on every launch until the bad file is removed, or only when the set of issues changes (remembered in preferences)? Recommendation: every launch. It is simpler and the file is still broken; a user who wants it gone removes the file.
