# Closing, dialogs and errors never strand the user

## Why

Several paths in TileShop.UI end with the user's work lost, the app stuck behind an invisible dialog, or menus and hotkeys bound to an editor that no longer exists. Each breaks the 1.0 goal (ARCHITECTURE §1): never lose work, never hit a control that silently does nothing. All were confirmed by reading the code; none were reproduced.

- **UI-SHELL, 1.0: closing the window can skip the save prompt.** `App.Desktop_ShutdownRequested` is `async void` and sets `e.Cancel` after awaiting `PrepareApplicationExit`, so the lifetime reads `Cancel` as false the moment the first prompt yields. `ShellView` has no `Closing` handler, so the title-bar X closes the main window before any prompt can run. File → Exit runs the sequence itself (`MenuView.Exit_Click`) and then calls `desktop.Shutdown(0)`, so it is a second, separate exit path.
- **UI-SHELL, 1.0: Escape strands an alert.** `OverlayDialog.OnKeyDown` on Escape, with no cancel option, calls `_dialogCompletion?.TrySetCanceled()` (always null: `ShowAsync` is never called on the `ShowMediatorAsync` path) and then animates out. The mediator never raises `Closed`, so `DialogHost` keeps the overlay in `Children`, `HasOpenDialog` stays true (hotkeys suspended, UI-SHELL-082) and the awaiting command never finishes. This hits every alert, including About. The same thing happens when a cancel option exists but cannot execute. The Enter path has the same flaw: it animates out after running the default option even when the mediator refused to close (validation failed, or `OnAccepted` returned false), leaving an invisible dialog. The close button and light dismiss also animate out before asking the mediator, which may refuse.
- **UI-EDITORS, 1.0: tab X leaves `ActiveEditor` stale.** `DockableEditorViewModel.OnClose` calls `_editors.Editors.Remove(_editor)` directly, skipping `CloseEditor`, so `ActiveEditor` keeps the closed editor. After the last tab closes, the Edit menu, File → Close/Save <name> and the hotkey scope stay bound to it.
- **UI-EDITORS, promoted: File → Close saves the project twice.** `CloseEditor` calls `RequestSaveUserChanges(editor, saveTree: true)`, which saves the containing project, then saves it again unless the editor is in Draw mode. `RequestSaveAllUserChanges` does the same: each prompt saves its project and the loop saves each project again. A redundant project save is another write-ahead log transaction that can fail after the user's data was already written. The stale commented-out lines in `CloseEditor` (`IndexedPixelEditorViewModel`) and `OpenEditor` (three deleted editor constructors) go with it.
- **UI-IMAGE-IO, promoted: export and import failures crash or lose work.** `ProjectTreeViewModel.ExportArrangerAs` asks for a file name before `AlertIfMissingDataSourceAsync`, and does not catch `ExportImage` failures (locked file, unwritable folder), which escape an async command. `ImportImageViewModel.OnAccepted` does not catch `ImageImportPreview.Commit` failures, so a read-only or locked ROM throws out of the dialog. Unhandled exceptions terminate the app (UI-SHELL Open items).
- **UI-IMAGE-IO, promoted, undecided: export ignores unsaved edits.** Export writes the arranger as last saved without telling the user (UI-IMAGE-IO-003), while import prompts (UI-IMAGE-IO-007). A user who exports to check their edits in an image editor gets the old pixels and may conclude the edits are gone.
- **UI-GRAPHICS-EDITOR, promoted: hidden status properties and stack traces.** `GraphicsEditorViewModel` redeclares `_activityMessage` and `_pendingOperationMessage` as `[ObservableProperty]`, hiding `ResourceEditorBaseViewModel.ActivityMessage`/`PendingOperationMessage`; the status bar binds by reflection, and `ArrangerDropHandler` writes through whichever static type it holds, so status text can silently not appear. The "Save Error" alert appends `ex.StackTrace`, which tells a user nothing they can act on.
- **UI-SHELL, promoted: window title.** `ShellView.Title` is "TileShop.Avalonia", shown in the taskbar and Alt+Tab.
- **UI-SHELL, promoted, undecided: no Save All.** Saving several modified editors means activating each tab and saving it, or exiting. Save Project As... is only on the project node's context menu (UI-PROJECT-TREE-057).
- **UI-EDITORS, optional: data file rename.** `OnTreeChanged` retitles editors whose `Resource` is the renamed node; a sequential editor's `Resource` is its own new `SequentialArranger`, and its data file is only `OriginatingProjectResource`, so its tab keeps the old name.

Found along the way, in scope because it is the same tab lifecycle: `DockFactory.Editors_CollectionChanged` removes a closed editor's dockable only from `_documentDock.VisibleDockables`. An editor floated into its own window lives in another dock, so File → Close <name>, a tree deletion or a project close removes the editor but leaves its floating tab open, bound to a closed editor.

## What

**One exit sequence.** The title-bar X, File → Exit, Alt+F4 and an OS shutdown request all run the same sequence: prompt for each modified editor, and on completion close projects, save preferences and shut down. The close or shutdown is cancelled synchronously, before any prompt, and re-issued only after the sequence completes, so Cancel always keeps the app open with every edit and project intact. A second close request while the sequence is running is ignored. After the sequence completes the app shuts down even if floating editor windows are open.

**Dialogs close only when their request closes.** Escape on a dialog runs its cancel option when it has one that can execute, and otherwise dismisses it like the title-bar close button (UI-SHELL-095): the request is cancelled, the overlay is removed, `HasOpenDialog` goes false and the awaiting command resumes. An alert dismissed this way returns as acknowledged. Every dialog animates out only after its request reports closed; a request that refuses to close (failed validation, a failed import commit, a refused cancel) stays fully visible and interactive.

**Every tab close goes through `EditorsViewModel.CloseEditor`.** The tab X, File → Close <name>, removal and project close use one removal path that updates `ActiveEditor`: closing the active editor activates the first remaining editor, closing the last leaves `ActiveEditor` null (Edit menu disabled, Close/Save <name> hidden, hotkey scope cleared), and closing an inactive tab leaves `ActiveEditor` alone. A closed editor's tab is removed wherever it is docked, floating windows included. Saving from a close prompt saves the containing project once; save-all saves each containing project once, after the prompts.

**Export and import report failures.** Export checks for a missing data file before asking for a file name; it prompts when an open editor on the arranger has unsaved changes (Yes saves first, No exports the saved state, Cancel stops); a write failure alerts "Export Error" with the reason. A failed import commit alerts "Import Error" with the reason and leaves the import dialog open so the user can retry or cancel. Both log the exception.

**Status and errors.** The graphics editor's status messages are the base class properties the status bar binds to. "Save Error" shows the message only; the stack trace goes to the log.

**Small shell items.** The window title is "TileShop". The File menu gains Save All, after Save <name>, enabled while any editor is modified, which saves every modified editor without prompting and then each containing project once (pending the open question). A sequential editor opened from a data file is retitled when that data file is renamed.

**Unchanged.** The save prompt's wording and Yes/No/Cancel semantics (UI-EDITORS-030 to 034); the first-remaining-editor activation rule (UI-EDITORS-037, 042); Enter running the default option (UI-SHELL-093); the import dialog's staging and blocking rules; the library's export and commit code (a commit that fails mid-way can still leave some elements written; the library has no transactional data write); Save Project As... stays on the project context menu only.

## Decisions

- **Cancel first, then ask.** The window's `Closing` handler and the lifetime's `ShutdownRequested` handler both set `Cancel = true` synchronously unless the exit was already confirmed, then start the exit sequence; on success the sequence marks the exit confirmed and calls `Shutdown`. Reason: Avalonia reads `Cancel` when the handler returns, so no awaited answer can ever reach it. Rejected: blocking on the prompt with a nested `Dispatcher.UIThread.MainLoop` inside `Closing` (works, but nested loops during shutdown re-enter close and dialog handlers; the tab-close path's nested loop is already a source of fragility); `ShutdownMode.OnExplicitShutdown` alone (still needs the `Closing` cancel).
- **The exit state is a plain, tested class.** A small `ExitGate` (names provisional) holds idle / running / confirmed and answers "may this close proceed, and should it start the sequence?"; `ShellView`, `App` and File → Exit consult it. Reason: the re-entrancy rules are the bug-prone part and cannot be exercised without a window otherwise (ARCHITECTURE §5). Rejected: flags spread over `App`, `ShellView` and `MenuView`.
- **File → Exit closes the main window.** Exit becomes a request to close the window, so there is one path. Rejected: keeping `Exit_Click`'s own sequence plus `Shutdown(0)`.
- **Escape with no usable cancel option dismisses.** It does exactly what the close button does: `Dismiss`, then `TryCancel`. Reason: the close button already has these semantics (UI-SHELL-095), and an alert's result is unused. A prompt without a Cancel choice (`YesNo`) returns `PromptResult.Cancel`, which its one caller (`ResizeTiledScatteredArrangerViewModel`) already treats as "not Yes". Rejected: Escape doing nothing on an alert (users expect Escape to close a message box); Escape running an alert's Ok (wrong for a future prompt whose only option is destructive).
- **The host animates out, not the key handler.** `OverlayDialog` only raises requests (option command, `Dismiss`); `DialogHost` animates the overlay out and removes it in its `Closed` handler. Reason: closing is the mediator's decision, and every bug above is the view closing without it. The key-to-action rule (Escape → cancel option if executable, else dismiss; Enter → default option if executable) moves into a static helper so it can be unit tested. Rejected: patching each branch of `OnKeyDown` separately.
- **One removal path for editors.** `DockableEditorViewModel.OnClose` calls `EditorsViewModel.CloseEditor` (keeping the nested loop Dock's synchronous `OnClose` needs) instead of removing from `Editors` itself. Reason: one place owns `ActiveEditor`. Rejected: having `ShellView` set `ActiveEditor` from Dock's focus events after a close (Dock may raise none when the last tab closes).
- **"First remaining editor" stays the activation rule.** Reason: it is already specified for File → Close and removal (UI-EDITORS-037, 042) and is testable without Dock. Rejected: activating the neighbouring tab (needs Dock's tab order, which drag reordering changes). DevTools checks that the shown tab and `ActiveEditor` agree after a close, since Dock picks its own active tab too.
- **Dockables are removed through the factory.** `Editors_CollectionChanged` removes the closed editor's dockable from whichever dock owns it, through the Dock factory, so floating windows are covered. Rejected: blocking floating (UI-SHELL-005 allows it).
- **Project saves once.** The prompt path keeps its project save (UI-EDITORS-031); `CloseEditor` drops its second save; save-all prompts with `saveTree: false` and saves each collected project once afterwards. Reason: identical behavior on both close paths, one transaction per project. Rejected: dropping the project save after an editor save entirely (the editor already saves its resource, but other pending tree state may rely on it; not verified, so out of scope).
- **Export prompts like import, without discarding.** When an open editor on the arranger is modified, export asks "Save Changes" Yes/No/Cancel: Yes saves then exports, No exports the saved state and keeps the edits, Cancel stops. Reason: the user learns what the PNG holds, and No must not destroy work that export does not need to touch. Rejected: silently exporting the saved state (today's surprise); exporting the editor's working pixels (needs a library export from an in-memory image, and makes export differ from the CLI); a status-bar note (easy to miss).
- **Import failures alert from the dialog and keep it open.** `ImportImageViewModel` takes `IInteractionService`; `OnAccepted` catches, logs, alerts "Import Error" (stacked above the dialog, UI-SHELL-090) and returns false. Reason: the staged preview and options survive for a retry once the file is writable. Rejected: showing the failure as the dialog's blocking message (that area means "fix the image", and it would disable Import).
- **Error alerts show the message, logs keep the stack.** Applies to "Save Error", "Export Error" and "Import Error". Reason: the stack trace is for the developer, and the log already records it.
- **Save All has no hotkey.** Window-wide hotkeys belong to the active editor (ARCHITECTURE §4), and Ctrl+Shift+S is not in any editor's set; adding a window-level hotkey category is out of scope.
- **Retitle sequential editors on data file rename.** The editor's `DisplayName` follows the data file's new name; the sequential arranger's own `Name` is not persisted, so it is left alone.
