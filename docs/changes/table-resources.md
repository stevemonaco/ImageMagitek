## Why

Games rarely store graphics at fixed offsets with fixed shapes. They store tables: one record per monster, map or screen, whose fields point at graphics, palettes, tile maps and further records. To expose those graphics today, a user finds the tables, works out each record by hand, and builds the project resources one by one. In practice that takes a script:

- FF4 has 223 monster records and FF5 384. The FF5 samples (`Samples/FF5MonsterSpritesViewer`, `FF5MonsterSpritesCLI`) are such a script in C#. A session building FF4's monsters needed another, in Python, writing project XML.
- The FireRed test project's 364 [metatile maps](metatile-maps.md), 62 metatile sets and their names came from a Python script that scanned the ROM for layout and tileset structures, then found the map headers and the region-map section names. The scan had to guess at structure. It counted three secondary tilesets short, and it filed shared layouts under names like "Celadon City +16 Indoor".

Those scripts produce snapshots. When a hack repoints a record, gives a monster another palette or moves a tileset, the generated resources still point at the old bytes, and nothing in the project records which record they came from. Each new game needs a new script, written by someone who can program.

## What

A **table definition** is a declarative XML file, data rather than code like the XML codecs ([LIB-CODECS](../specs/lib/codecs.md)), that describes a game's tables precisely enough to generate project resources from them. Generation creates ordinary resources: scattered arrangers, palettes, compressed data, tilemaps, metatile sets and metatile maps. A project built this way loads without the definition.

Two phases, each useful on its own:

**1. Definitions and generation.** A definition describes:

- **Address space.** How the game's pointers map to file offsets: built-in mappers for SNES LoROM and HiROM (with or without a copier header), GBA (`0x08000000`), NES and Game Boy banked ROM, and linear.
- **Record types.** Named layouts of fields, each a bit range with endianness and a kind: an integer, a pointer (mapped through the address space), or a pointer to another record type, which generation follows. FF4's graphics record is `size:8 palette:8 pointer:16le`. A FireRed map header is `layout:ptr→Layout events:ptr ... mapsec:8@0x14`, a layout is `width:32 height:32 border:ptr blocks:ptr primary:ptr→Tileset secondary:ptr→Tileset borderWidth:8 borderHeight:8`, and a tileset is `compressed:8 secondary:8 tiles:ptr palettes:ptr metatiles:ptr callback:ptr attributes:ptr`.
- **Tables.** A record type at a base address, with a stride and a count. The count is a literal, an expression over fields, a sentinel value that ends the table, or a list literal for tables of tables whose group sizes the game keeps only in code (FireRed's 43 map groups). A table may be a table of pointers to records.
- **Expressions.** Small integer expressions over fields, lookups and the record's own index, for addresses, palette entry counts, dimensions and derived counts, for example `0x48000 + (pointer & 0x7FFF) * 8`, or a secondary tileset's metatile count as `(attributes - metatiles) / 16`. A record can have **variants** selected by a predicate (FF4's `size & 0x80` selects the boss path).
- **Text.** A **charmap** maps byte values to characters for a game's text encoding, with a terminator. A name table is a table of pointers to strings, or of fixed-width strings, read through a charmap, such as FireRed's region-map section names, indexed `mapsec - 0x58`. Name **overrides** replace a value's name where the game's own table is misleading (FireRed's catch-all section `0xC4` reads "CELADON DEPT.").
- **Outputs.** Each output element turns one record into one resource of a given type, with its attributes taken from fields and expressions: a scattered arranger (with the `rect`, `mask` or `indexmap` layout), a palette, a compressed data block (for a pointer field marked compressed), a tilemap, a metatile set or a metatile map. An output can name the resources other outputs create for related records. A FireRed metatile map lists the metatile sets made from its layout's primary and secondary tileset records.
- **Names and folders.** A name template and a folder template per output, for example `Maps/{sectionName}/{sectionName} {kind} {n}`, built from fields, lookups and text, with rules for duplicates (number them, or append the record address).

"Generate Resources from Table..." on a data file loads a definition and lists the records each output would produce, with a thumbnail, name, folder and size. The user picks a target folder and generates. The CLI gets a `generate <project> <datafile> <definition> <folder>` verb with `--dry-run`. Generation writes all resources in one project transaction, writes the manifest, and prints a report: resources created, records skipped with their reason, and any warnings (for example a declared count smaller than the numbers the maps use, raised to the highest used).

**2. Regeneration.** Running the same definition into the same folder again rebuilds the resources listed in the folder's manifest and reports what changed (records added, removed, repointed, re-paletted). Resources the user created in that folder are left alone. The manifest is an open XML format, so another program can generate resources and a manifest that TileShop then regenerates and reports on.

Moving data (relocating a record's graphics to free space and rewriting its pointer) is not part of this proposal; see Decisions.

### Worked example 1: FF4 monsters (flat)

One table of 223 graphics records (`size:8 palette:8 pointer:16le`) with a size-class lookup table of (width, height) pairs. A variant on `size & 0x80` selects the boss path, whose layout is an `indexmap` with skip codes. Bit 15 of the pointer selects 4bpp tiles. Monster names come from a fixed-width name table read through FF4's charmap. The outputs are one scattered arranger per monster and one palette per distinct palette address, plus an optional overview arranger. This is what phase 1 of the original proposal covered, unchanged.

### Worked example 2: FireRed maps (nested)

- The map groups table holds 43 pointers to arrays of header pointers, with a list-literal count per group. A header's `layout` field is a pointer to a Layout record, whose `primary` and `secondary` fields are pointers to Tileset records.
- 425 headers reach 309 distinct layouts, which share 2 primary and 60 secondary tilesets.
- **Outputs:**
  - one compressed data block per tileset's `tiles` (or an uncompressed tile range when `compressed` is 0);
  - 7 palettes per primary and 6 per secondary tileset;
  - one metatile set per Tileset record, with count 640 for a primary and `(attributes - metatiles) / 16` for a secondary;
  - one metatile map per Layout record, listing its two sets at bases 0 and 640;
  - one border map per layout.
- **Names:** the section name of the headers that use the layout. An outdoor layout (map type 1–3) takes the bare section name, and other kinds are numbered. A layout used by several sections takes the name of its most common one.
- **Not reached through any header:** the scan's 55 unused layouts. They are not generated unless the definition adds a table that lists them.

The generated project should match the scratchpad script's 364-map result for every layout that a header reaches. Exceptions: the corrected secondary metatile counts, and names where the script guessed.

## Decisions

- **Definitions are data first; plugins cover the rest.** A declarative definition covers fixed-stride records, bit fields, pointers to records, lookups, expressions, variants, text and the three arranger layouts. Those are everything the FF4 and FF5 monster tables and FireRed's maps need. A game whose structure is procedural uses a **generator plugin**: a contract that takes the data file's bytes and returns record descriptions (outputs with their attributes), with no core types. Reason: this follows the codec decision (XML first, C# when a format cannot be expressed), and the FF5 samples can become such a plugin. Rejected: plugins only (every game needs C#); a general scripting language (scripting is a non-goal and a security surface).
- **Records can point at records.** A pointer field may name the record type it points to, and generation follows it. Reason: map, tileset and sprite data are trees, not flat tables (FireRed: groups → headers → layouts → tilesets), and flattening them in the definition would repeat the shared records. Rejected: lookups only, which the original proposal had and which cannot reach a record through a pointer.
- **One resource per record instance.** Records reached by several paths are identified by record type and address, and their outputs are generated once and referenced by key. Reason: 425 FireRed headers reach 309 layouts and 62 tilesets, and one metatile set per reference would make 300 copies of the primary tileset that could disagree. Rejected: one resource per reference.
- **A small expression grammar, not fixed attributes.** Integer literals in decimal or hex, field, lookup and index references, `+ - * / % & | ^ << >> ~`, comparisons, `?:`, and `min`/`max`. Reason: real pointers and counts need masks, scales, bank arithmetic and conditions (FF4's pointer bit 15 selects 4bpp tiles; FireRed's secondary metatile count is a pointer difference). Rejected: embedding C# or Lua expressions.
- **Counts are declared, and generation checks them.** A table or output count comes from the definition. When a generated metatile map uses numbers past a set's declared count, generation raises the count to the highest number used and reports it. Reason: FireRed does not store secondary metatile counts, and the pointer-difference rule undercounts three tilesets whose attributes are not stored right after their metatiles. Rejected: failing generation (the maps are correct data); silently inferring counts from usage alone (undercounts sets whose last metatiles are unused).
- **Generated resources are ordinary resources.** Generation writes the existing resource types with no reference to the definition. Reason: a project loads without the definition, as with [container scanners](container-scanners.md), and nothing in the project format has to change. Rejected: a live `table` resource rendered from the current bytes on every open (see Open questions).
- **Definitions are files, not project resources.** A definition lives anywhere, typically next to the project as `<game>.table.xml`, and may reference charmap files beside it. Reason: the project reader skips XML whose root is not a resource (LIB-PROJECT-FORMAT-005), so definitions can sit in the project directory, and one definition can serve several projects for the same game. A shipped `_tables` folder is not planned: tables are per game and per revision.
- **Regeneration owns only what it created.** A generation run writes a manifest listing the resource keys it created and the record each came from. Regeneration replaces those resources and deletes the ones whose record no longer exists, after a confirmation that lists them. Reason: the project format has no "generated by" marker. Rejected: regenerating a whole folder (deletes the user's own resources); tracking by name pattern (breaks on rename); a live `table` project resource (user decision: a format change and a load-time dependency on the definition).
- **The manifest is an open format.** The manifest is an XML file (`<game>.manifest.xml`, beside the definition) validated by a published schema (`TableManifestSchema.xsd`) and documented in LIB-TABLES, and TileShop treats a manifest written by another program exactly like its own. Reason: the user wants the ecosystem not boxed around TileShop and C#; a decompilation exporter or a script in any language can generate resources plus a manifest, and TileShop can then regenerate or report on them. XML matches the definitions and the project format and has a schema language TileShop already uses. Rejected: JSON (no schema in use in the project yet, and the user was unsure about it); a TileShop-private format.
- **Charmaps are shared files.** A charmap is a small XML file per text encoding (for example `gen3.charmap.xml`), validated by `CharmapSchema.xsd` and referenced by path from any definition. Reason: games of one engine share an encoding (FireRed, LeafGreen and Emerald), and the user chose one shared file per encoding. Rejected: charmaps inline in each definition.
- **FireRed maps drive phase 1.** The first implementation is built and checked against the FireRed definition (nested records, shared-record deduplication, metatile outputs), with the scratchpad script's 364-map result as the reference; the FF4 definition follows. Reason: user decision; FireRed exercises the new parts of the design and has a known-good result to compare against. Rejected: FF4 first (flat records only); both at once (the largest change).
- **Name overrides are part of the definition.** Reason: a game's own text tables are sometimes wrong or misleading for a project tree (FireRed section `0xC4`), and the fix belongs with the definition that every user of that game shares, not in each project. Rejected: renaming after generation (lost on regeneration).
- **Relocation is a separate proposal.** Moving a record's data to free space and rewriting its pointer reverses an ARCHITECTURE non-goal and needs a free-space model, which re-tile import in [tilemaps](tilemaps.md) also needs. The two will be designed together. Reason: generation and regeneration are useful without it, and keeping it out lets them ship without the non-goal change. Rejected: relocation as phase 3 of this proposal (the original plan).

## Spec changes

- **New spec `docs/specs/lib/tables.md` (LIB-TABLES):** the definition schema (`TableSchema.xsd`), the charmap schema (`CharmapSchema.xsd`), the manifest schema (`TableManifestSchema.xsd`) documented for other programs, address mappers, record types and fields, pointer following, tables and counts, the expression grammar and its errors, variants, charmaps and text, outputs and their attributes per resource type, names, folders and duplicates, record-instance deduplication, the generator plugin contract, generation into resources and its report, the regeneration manifest.
- **LIB-PLUGINS:** the generator plugin kind, added to `ImageMagitek.Plugins.Contracts` as a minor version.
- **LIB-PROJECT-SERVICE:** generate into a folder in one write-ahead-log transaction; regeneration (replace, delete with confirmation).
- **LIB-METATILE-MAPS / LIB-TILEMAPS:** none to their behavior; generated metatile sets, metatile maps and tilemaps are ordinary resources.
- **UI-PROJECT-TREE:** "Generate Resources from Table..." on a data file; regeneration from the folder's context menu.
- **New spec or UI-EDITORS section:** the generation dialog (definition picker, output list with thumbnails, names and folders, target folder, report).
- **CLI-COMMANDS:** the `generate` verb, its exit codes, `--dry-run` printing the outputs and the report.

## Tasks

1. **Draft spec.** LIB-TABLES with `status: draft`, requirements before code.
2. **Definition format.** XSD, reader, validation, address mappers, record types, tables, charmaps. Tests: each mapper round-trips addresses; malformed definitions fail naming the element and attribute; unknown field, record type or charmap references fail at load, not at evaluation.
3. **Evaluation.** Fields, pointer following, tables with every count form, lookups, expressions, variants, text, and record-instance identity, run over a `DataSource`. Tests: synthetic fixtures for bit fields at every alignment and endianness; expression precedence, `min`/`max` and division by zero; a two-level pointer tree in which two parents share one child yields one instance; a sentinel-terminated table; a pointer past the end of the file is reported per record, not thrown.
4. **Outputs and generation.** Every output type through `ProjectService` in one transaction, names, folders, duplicates, the count check and the report. Tests: generated resources save and reload with no definition present; a shared child record becomes one resource referenced by both parents' outputs; palettes are deduplicated by address and entry count; names are sanitized and unique; an undercounted metatile set is raised and reported.
5. **Fixtures.** A FireRed (BPRE revision 0) definition first, then an FF4 (FF2 US) definition, kept in the repo as documentation with the shared `gen3` charmap, with synthetic test data shaped like them, since ROMs are not in the repo. Manual: generate FireRed's maps into a copy of the FireRed project and check every layout reached by a header against the scratchpad script's CLI export (pixel-identical); generate FF4's monsters and compare with the game, including palette swaps and Zeromus.
6. **UI and CLI.** Generation dialog with preview and report; `generate` verb with `--dry-run`.
7. **Regeneration (phase 2).** Manifest, diff and confirmation. Tests: added, removed and changed records; user-created resources in the folder survive. Manual: hex-edit one FireRed layout's block map pointer in a ROM copy, regenerate, and check that only that map changes.
8. **Close.** Make LIB-TABLES current, update the specs above, and remove the backlog lines resolved.
