# Ship 1.0

## Why

1.0 needs a build that is produced, versioned, documented and checked the same way every time. Today none of that holds:

- [ARCHITECTURE] CI: `.github/workflows/ci.yml` is a Nuke-generated workflow that runs `./build.cmd Package`, which no longer exists, only on `workflow_dispatch`, with no tests.
- [CLI-PUBLISH] The two tracked `.pubxml` profiles target `net7.0` (CLI-PUBLISH-013). `FolderProfile.pubxml.user` is orphaned, but it and the other `*.pubxml.user` files are untracked (`*.user` is gitignored), so removing them is a local cleanup, not a repo change.
- [CLI-PUBLISH] `publish.ps1` keeps going after a failed build or test (CLI-PUBLISH-003), ignores `-ReadyToRun` (CLI-PUBLISH-006), applies the `$CliVersion` fallback after the zip name is built (and the parameter is mandatory, so the fallback is dead), and a rerun fails at `Compress-Archive` without `-Force`. Also found: `-Version`/`-CliVersion` only name the zips. The binaries carry `Directory.Build.props`' `0.993-preview`, so `-Version 1.0` produces a zip named 1.0 with 0.993 inside. The publish folders are overwritten but never emptied, so files left from an earlier publish end up in the zip.
- README: says .NET 6, lists Autofac, Jot and Nuke (none are referenced any more; DI is `Microsoft.Extensions.DependencyInjection`), leads with an old WPF screenshot, and does not document the CLI.
- Release notes: the codec behavior changes recorded in LIB-CODECS ("Codec rework behavior changes") and the format changes from [project-format-freeze.md](project-format-freeze.md) reach users nowhere.
- Dead code: `ImageMagitek.Services/Actions` (`IMagitekAction` and its records, `IActionHistory`), `ImageColorAdapter` (every member throws), `PixelRemapOperation.RemapByAnyIndex` (empty branches; the commented `CanRemapByAnyIndex`), `ProjectService.FindStaleKeyResources` (private, never called). Each was confirmed to have no references outside its own file and the specs.
- (promoted) The backlog's "Manual checks" section and [UI-SHELL] "the debug load button exists only in Debug builds". These are checks DevTools cannot drive, pending from earlier milestones. For 1.0 they become a release checklist run on the published Release artifact. The DevTools cannot attach to a Release build at all, so a Release-only regression (trimming in the CLI, the Debug-only code paths) is caught only by a manual pass on the artifact users download.

Versioning, found while checking the code: the version lives in `Directory.Build.props` (`VersionPrefix` 0.993, `VersionSuffix` preview). Help → About (UI-SHELL-043) reads `FileVersionInfo.GetVersionInfo(Assembly.GetExecutingAssembly().Location).ProductVersion`. In the single-file published build `Assembly.Location` is empty and `GetVersionInfo("")` throws, so About fails in exactly the build users get (found by reading, not reproduced). The CLI prints a hard-coded `"TileShopCLI v0.992 by Klarth"` (CLI-COMMANDS-001), while `--version` (CommandLineParser `AutoVersion`) prints the assembly's informational version, so the two disagree.

## What

- **CI.** Every push and pull request builds the solution and runs the unit tests in Release on `windows-latest`. A tag `v<version>` runs `publish.ps1` and creates a draft GitHub release with the zips attached and the release notes as its body. The owner publishes the draft after the release QA pass.
- **One version.** `Directory.Build.props` `VersionPrefix`/`VersionSuffix` is the only version number. UI, CLI and both zips carry it. About and the CLI banner read the entry assembly's `AssemblyInformationalVersionAttribute`. `publish.ps1` reads the version from MSBuild and no longer takes version parameters.
- **publish.ps1** stops with a non-zero exit at the first failed command, empties `publish/<rid>` first, overwrites zips, and drops `-ReadyToRun`, `-Version` and `-CliVersion`. The `.pubxml` profiles are deleted; `publish.ps1` is the only way to package.
- **README** is current (stack, dependencies, build, CLI usage with verbs, options and exit codes). **Release notes** live in `docs/release-notes/1.0.md`.
- **Dead code** listed above is deleted, with the specs that list it.
- **Release QA pass.** The checklist below is run on the draft release's win-x64 zip on a machine without the .NET SDK. Results are recorded here.

Unchanged: what `publish.ps1` builds (self-contained, single-file, trimmed CLI), the zip layout, every runtime behavior apart from About and the CLI banner.

## Decisions

- **One version for UI and CLI, in `Directory.Build.props`.** They ship from one commit and share the library and the project format, so separate numbers only raise "which CLI goes with which UI". Rejected: the separate `-CliVersion` (CLI-PUBLISH-001), and passing the version on the command line (it already let the zip name and the binaries disagree).
- **Release procedure.** The release commit sets `VersionPrefix` to `1.0.0` and removes `VersionSuffix`. The tag job fails unless the tag equals `v` + MSBuild's `Version`. After the release, `VersionPrefix` moves to the next version with `VersionSuffix` `preview` again. Reason: the version is in source, so any checkout builds what it says; the tag check stops a mistagged release. Rejected: deriving the version from the tag (local builds would not know their version) and tools such as MinVer/Nerdbank (a dependency for one number).
- **About and the banner read `AssemblyInformationalVersionAttribute`.** It is set from the same MSBuild `Version` plus the SDK's `+<commit>` suffix, and it works in single-file builds. About shows the full informational version, because the commit hash identifies a build in bug reports. The CLI banner shows it too; the banner wording belongs to [cli-1-0.md](cli-1-0.md), which this proposal only feeds. Rejected: `FileVersionInfo` on `Assembly.Location` (empty in single-file), and `Assembly.GetName().Version` (drops the suffix and the commit).
- **CI builds and tests in Release.** That is the configuration that ships: the Debug-only debug load button and DevTools are compiled out, and the license-keyed `AvaloniaUI.DiagnosticsSupport` packages are Debug-only, so CI needs no Avalonia license secret. Rejected: Debug CI (it tests a build nobody downloads).
- **CI on `windows-latest` only.** The solution contains the WPF sample (`net10.0-windows`), and the project is developed and checked on Windows. A Linux leg for the library tests can be added later. It depends on the supported-platforms question below.
- **Draft release, published by hand.** The tag job uploads to a draft. The owner publishes it after the QA pass on those exact zips. Rejected: publishing from the tag job (the QA pass would run after users can download).
- **`publish.ps1` fails fast.** `#Requires -Version 7.3` with `$ErrorActionPreference = 'Stop'` and `$PSNativeCommandUseErrorActionPreference = $true`, so a failing `dotnet` call stops the script. The script already needs PowerShell 7 (multi-argument `Join-Path`). Rejected: checking `$LASTEXITCODE` after each call (easy to miss one).
- **Drop `-ReadyToRun` rather than wire it up.** No one passes it, and ReadyToRun's startup gain and size cost were never measured. Shipping it untested is not hardening. It can return as a measured change (backlog line).
- **Delete the `.pubxml` profiles.** They target a framework the project no longer builds and duplicate `publish.ps1` with different settings (framework-dependent). Rejected: updating them (two packaging paths that can drift).
- **Release notes as one file per version** (`docs/release-notes/<version>.md`), used verbatim as the GitHub release body. The tag job fails when the file is missing. Rejected: a growing `CHANGELOG.md` (the release body then needs extracting) and notes written only on GitHub (not reviewed with the code).
- **CLI usage in the README.** Toolchain users find the CLI from the repository page. The README documents verbs, options and the exit-code table, checked against `TileShopCLI --help` from the published build. Rejected: wiki only (not versioned with the code).
- **QA results are recorded in this proposal.** Each item is checked off here as it passes. A failure goes to `docs/BACKLOG.md`, tagged **1.0** when it meets the ARCHITECTURE §1 bar, and blocks publishing the draft until fixed and rechecked. When 1.0 ships, this file is deleted like any proposal and git history keeps the record. Rejected: a separate QA log file (one more document to keep current), and running every `manual —` requirement in the specs (about 180, most verified when built). The pass is the pending checks plus a smoke test of what differs in a Release single-file build.

## Open questions

- **Which runtimes ship at 1.0?** `publish.ps1` accepts win-x64, osx-arm64, osx-x64 and linux-x64, but only Windows is developed and checked. Building macOS on Windows produces unsigned arm64 binaries that macOS refuses to run, and building on Linux or macOS runners fails on the solution's WPF sample unless the script builds only the shipped projects. Recommendation: ship win-x64 as the supported 1.0 platform. Attach linux-x64 and osx-arm64 from native runners (`ubuntu-latest`, `macos-latest`, with the script building only TileShop.UI, TileShop.CLI and the tests) labeled "untested" in the release notes, and leave osx-x64 out.
- **Codec XML authoring guide and plugin authoring guide (backlog, untagged).** Plugins load in both UI and CLI at 1.0, and XML codecs are the project's default way to add a platform (ARCHITECTURE §6). Recommendation: for 1.0, write a short codec XML authoring guide (`docs/codec-xml.md`: flow vs pattern, the schema attributes, dropping a file into `_codecs`, checking it with the sequential view). A user can act on it with no further support, and the XML format is already frozen by the shipped codecs. Defer the plugin authoring guide and packaging `IndexedCodecContract` to 1.1. Documenting the plugin API makes `IGraphicsCodec` and friends a public contract, and nothing has decided to freeze them.
